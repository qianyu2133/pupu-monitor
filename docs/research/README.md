# 前期调研归档

这两份是项目启动阶段的调研报告，**写于还没有任何代码之前**。保留是为了记录当时的判断依据，但部分结论已被后续实证修正——看的时候请以文首标注为准。

## 01-可行性调研.md

立项时的技术与合规评估：两个平台的接口差异、反爬与风控、通知渠道、法律边界。

**仍然有效的判断**
- 朴朴接口是标准 REST + JSON，鉴权靠 `Authorization` + `pp-userid`，可行性高
- 小象超市无可用 H5 入口，需 `mtgsig1.2` 动态签名，只能走安卓自动化
- 「几秒刷新一次」是伪需求：服务端有缓存，固定高频最容易被风控打标 → 已实现分层轮询（12s / 180s + 抖动）
- 加购 ≠ 锁库存，提交订单才锁（约 15 分钟支付窗口）
- 只读本人账号、低频、个人自用风险低；做成多用户 SaaS 或自动下单则性质改变

**已被推翻的判断**
- 「删除/下单是写操作，必须录制模板替换 id」→ 实测删除是 `selected_count=0`，下单是「重建结算 → 提交」，都不需要模板替换
- 「微信服务号模板消息走不通，只能用企业微信」→ 结论正确，已采用企业微信群机器人

## 02-软件化调研.md

打包成桌面软件的可行性、工作量、风险。

**已被推翻的判断**
- ~~「手机连电脑代理这一步去不掉」~~ → **错**。微信 PC 版能开小程序，流量走 Windows 系统代理，全程不需要手机。这条一改，可行性从 70% 提到 80%
- ~~「换收货地址必须重录下单模板」~~ → **错**。下单时按当前选中地址重写 `store_id`/`place_id`/`receiver*` 即可

**仍然有效的判断**
- 杀毒软件误报是长期成本，签名证书 1000~3000/年
- 接口改版是主要维护成本 → 规则热更新应做（待办）
- 小程序若开 SSL Pinning，方案立即失效 → 抓包层保持可替换
- 分发范围决定项目性质：自用 / 小范围分享可行，收费有判例风险
