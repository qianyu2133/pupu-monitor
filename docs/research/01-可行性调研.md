# 「小象 / 朴朴 出清商品 + 购物车降价监控」可行性调研

> 结论先行：**能做，但不是"两个平台一样做"**。朴朴可以纯接口实现（1~2 天出 MVP）；小象超市需要绕开美团 mtgsig 签名，不建议逆向，建议用安卓自动化/浏览器代签兜底。核心风险不在技术，而在**账号风控**和**"锁单"这一步的合规边界**。

---

## 一、先把需求拆成 4 件事，难度完全不同

| # | 需求 | 技术性质 | 难度 | 风险 |
|---|---|---|---|---|
| 1 | 采集出清商品池 | 读接口 / 读页面 | 中 | 中（高频爬取易触发风控） |
| 2 | 把指定商品加进购物车 | 写接口 / 点击 UI | 中高 | 中高（写操作风控更敏感） |
| 3 | 几秒级刷新购物车比对价格 | 读接口 + 定时 | 低 | 中（频率是唯一变量） |
| 4 | 降价通知 + 询问是否锁单 | 推送 + 交互回执 | 低 | 低 |
| 5 | 自动"锁单"（提交订单占库存） | 自动下单 | 高 | **高（不建议做）** |

**关键认知**：加购物车 ≠ 锁库存。两个平台都是**提交订单才锁库存**（一般 15 分钟支付窗口）。所以"锁单"本质是"自动下单"，这是整个项目里唯一碰钱、碰平台协议红线的动作，必须由人点最后一下。

## 二、两个平台的真实技术底牌（实测/公开资料）

### 2.1 朴朴超市 —— 可行性：★★★★★（推荐先做）

- **有真实 H5 商城**：`ma.pupumall.com`，接口域名 `*.pupuapi.com`，是标准 REST + JSON。
- **鉴权方式简单**：抓包拿到 `refresh_token`（登录接口 `/clientauth/user/verify_login` 返回体里），换出 `Authorization` + `pp-userid` 两个头即可长期调用，**没有动态签名**。开源脚本（如 CHERWIN_SCRIPTS 的 `PPCS.py`）已验证这套 token 机制可用多年。
- 请求只需固定头：`User-Agent`（可伪装微信环境）、`Origin/Referer: https://ma.pupumall.com`、`pp-os: 0`。
- **意味着**：购物车轮询、出清频道拉取、加购，全部可以用纯 HTTP 完成，不需要手机、不需要云手机。
- ⚠️ 变动风险：2026 年 7 月阿里收购朴朴并接入淘宝闪购，整合期接口可能迁移/合并，需要留适配层。

### 2.2 小象超市（原美团买菜）—— 可行性：★★★☆☆（能做，但成本高）

- **没有可用的 C 端 Web 商城**。`maicai.meituan.com` 只是品牌宣传页，实测抓取确认无商品/购物车/登录。真实入口只有：美团 App、微信小程序、支付宝小程序。
- 接口在 `mall.meituan.com`，请求头必须有 **`mtgsig` 签名（当前为 mtgsig1.2 一代）**，另需 `csecuuid`、`userid`、`req_of_maicai` 等参数。签名随「请求体 + 时间 + 页面路径 + 设备指纹」变化，**抓一次包拿到的签名不能复用**。
- 公开的逆向分析（CSDN 等）都存在，但：JS 被 OB 混淆 + 云函数化，**每次发版都可能失效**，维护成本是无底洞。
- 三条可行路径（按推荐度）：
  1. **安卓自动化**（真机 or 云手机 + uiautomator2/Appium）：完全不碰签名，让 App 自己算。稳定性和"抗改版"最好，但有设备成本。
  2. **浏览器代签**：用 Playwright 加载美团 H5 页面，借页面自身 JS 生成签名后再发请求。理论上可行，但小象缺 H5 商城入口，落地不确定，属于"能试但别指望"。
  3. **逆向 mtgsig**：能做，不建议。等于和美团风控团队持续对抗。

## 三、5 条技术路线对比

| 路线 | 适用平台 | 实现成本 | 秒级能力 | 抗改版 | 风控暴露 | 结论 |
|---|---|---|---|---|---|---|
| **A. 纯 HTTP 接口轮询** | 朴朴 | 极低（1~2 天） | ✅ 5~10s | 中 | 中 | **朴朴首选** |
| **B. Playwright 驱动 H5** | 朴朴（有 H5） | 低（2~3 天） | ✅ 10~20s | 高（DOM 变了才挂） | 低（就是真浏览器） | 可做加购/截图兜底 |
| **C. 安卓自动化 + 真机** | 两者通用 | 中（3~5 天） | ✅ 10~30s | 中（UI 改版即挂） | 中高（设备指纹） | **小象首选** |
| **D. 云手机托管** | 两者通用 | 中（同 C + 40~80 元/台/月） | ✅ | 中 | 中高 | 长期托管方案 |
| **E. PC 微信小程序 + UI 自动化/OCR** | 两者通用 | 低 | ❌ 慢、脆弱 | 低 | 低 | 只适合验证想法 |

**组合推荐**：`朴朴走 A（+B 做加购）`，`小象走 C（闲置安卓机即可，不必上云手机）`。

## 四、几个真正的难点，以及破解方式

### 难点 1：出清商品不是一个固定入口
两个平台的出清都散在「晚间清仓 / 低价捡漏 / 今日特价」频道 + 商品标签（出清、临期、清仓）+ 库存紧张状态里，**没有稳定的"出清 SKU 列表"接口**。

破解：双策略并行
- **频道扫描**：定时拉「清仓频道」全量列表，用 `折扣率 = 现价/原价` + 标签关键词（出清/临期/清仓/买一送一）过滤，命中进候选池。
- **白名单扫描**：只盯你常买的 20~50 个 SKU（搜商品名拿 sku_id），请求量小 10 倍，风控友好。

### 难点 2："几秒钟刷新一次"其实没必要，而且有害
- 服务端价格有缓存，5s 轮询大概率拿到同一个值，纯浪费请求。
- 风控判定看的是**频率稳定性**：固定 5s 一次的机器节奏最容易被打标。

破解：分层轮询
```
21:00-23:30（出清高峰）：10~15s + ±30% 随机抖动
其他时段：120~300s + 抖动
连续 N 次价格不变 → 自动退避到 60s
```
单账号总请求量控制在 **< 1 req/s**，且不要并发打同一个 host。

### 难点 3：通知要能"回答"，微信个人主体做不到模板消息
- 微信**服务号模板消息需要企业主体认证**（300 元/年），个人号走不通。
- 免费可用的最佳解：**企业微信自建应用消息** —— 免费、额度宽松、能推到个人微信、支持 Markdown/图文/可点链接。
- 快速验证：Server 酱 Turbo（免费 5 条/天，8 元/月）；iOS 可加 Bark 做锁屏强提醒。
- **"是否锁单"的回执**：自建一个带签名 token 的 H5 确认页（`/ack?item=xxx&t=xxx`），通知里放链接，点"已锁单/忽略"写回数据库。普通 https 域名微信内可直接打开（需备案，别用裸 IP）。

### 难点 4：通知到了，货已经没了
出清品库存常常个位数，从"降价"到"售罄"可能只有 1~2 分钟。**这个项目的定位应该是"帮我盯价格、别错过窗口"，不是"保证抢到"。** 想抢到就得自动下单，这就进红线了。

## 五、合规红线（必须知道）

1. **个人自用、低频、只读自己账号的数据** → 民事/刑事风险很低。最高检 2025 年明确表态：单纯违反 robots、仅爬取公开数据**不宜入罪**；入罪的是"破解加密接口获取非公开数据"。
2. **红线一**：不要逆向/绕过加密签名去批量拉取**非本人**的数据（有判例：破解 App 加密接口获取用户数据，判 1 年 9 个月~3 年）。
3. **红线二**：不要做成对外售卖的多用户 SaaS。绕开风控批量采集商品数据，被判**不正当竞争、赔偿 500 万**的判例已有多起（2025 最高法典型案例）。
4. **红线三**：不要自动化提交订单/支付。平台协议明确禁止，且可能被认定为干扰交易秩序；也是账号被封的最快路径。
5. 现实代价：账号被限权/封禁，购物车、优惠券、会员权益一起没。**用一个不常用的小号跑更稳妥**。

## 六、推荐架构

```
┌─────────────── 采集层（可插拔 Adapter） ───────────────┐
│  pupu_http      朴朴 REST 轮询（token）                 │
│  pupu_browser   Playwright 驱动 H5（加购/兜底）         │
│  xx_android     uiautomator2 驱动小象 App（签名交给App）│
└──────────────────────┬───────────────────────────────┘
                       ▼
        标准化模型 Item{platform, sku_id, name, price,
        origin_price, discount, stock, tags[], captured_at}
                       ▼
        变更检测（sku 维度 price hash 对比）→ price_history
                       ▼
        规则引擎（目标价 / 降幅阈值 / 出清标签 / 库存阈值）
                       ▼
        通知（企业微信应用消息 / Server酱）→ 确认 H5 回执
                       ▼
        观测（日志、失败告警、轮询退避、token 过期提醒）
```

技术选型建议（按你熟悉度可换）：
- 后端：Python + FastAPI + APScheduler（单机够用，别上微服务）
- 存储：SQLite 起步（单用户场景完全够），后续换 Postgres
- 前端：一个单页控制台（Vue/React 皆可），管 token、监控列表、看价格曲线
- 部署：家里的旧电脑 / 树莓派 / 轻量云 2C2G（50~100 元/月）

## 七、MVP 路线（建议照这个顺序做）

**P0 · 打通核心链路（1~2 天）**
朴朴抓包拿 refresh_token → 脚本读购物车 → 落地 SQLite → 价格变化推企业微信。
验收：手动把购物车里某商品降价，90 秒内收到微信通知。

**P1 · 变成能用的产品（3~5 天）**
Web 控制台（token 管理 / 监控清单 / 价格曲线）+ 目标价规则 + 出清频道扫描 + 确认回执页。

**P2 · 接入小象（1~2 周）**
优先安卓自动化；用闲置安卓机跑一台，不要一上来买云手机。

**P3 · 稳定性**
token 自动续期、失败告警、多账号隔离、轮询退避、接口变更监控。

## 九、一句话结论

**朴朴能做得很漂亮，小象能做得比较脏但能用。** 建议先用朴朴跑通"监控→降价→通知→回执"闭环（一周内可交付），验证你真实的捡漏收益；确认值得长期跑之后，再为小象补一台安卓执行端。**自动锁单不做**，做到"一键跳到结算页、手指点最后一下"就是最优解。
